## The five asks (user, 2026-10-21, paraphrased)

1. **Icons per machine** — by muscle group, cardio, or machine type — so a
   machine is recognised at a glance in every list.
2. **"Next" is wrong in a free workout**: it names whatever machine was
   opened last, not what should come next.
3. **Cardio machines take a level** (resistance step, e.g. a rower's 1–10),
   logged per set.
4. **A default number of sets (3), configurable**, and per machine or
   exercise: once an exercise has its sets, the workout should steer to the
   others — what still lacks its sets must be easy to see.
5. **Session progress by muscle** — which muscles the active workout has
   trained, as bars.

## Data model (foundation, done first on main — F0)

- `settings.defaultSets` (default 3, whole number ≥ 1). In merge.js
  `USER_SETTINGS` (it syncs, like `restSeconds`); `cleanSettings` repairs it
  through `numFields`.
- `machine.targetSets` (optional whole number ≥ 1; absent = the default) and
  `machine.exerciseSets` (`{ [exercise]: n }`, locker-style: absent when
  empty; an exercise removed from the machine takes its entry with it).
  `isValidMachine` refuses a non-finite `targetSets` like a bad
  `restSeconds`, and an `exerciseSets` that is not a plain object of finite
  numbers like a bad `grips`.
- `setGoalFor(machine, exercise, settings)` (store.js) is THE resolution:
  `exerciseSets[exercise]` → `targetSets` → `settings.defaultSets` → 3, as a
  whole number ≥ 1; **null for a cardio machine** (one bout, never a tally)
  and for no machine.
- `setTargetSets(machineId, exercise|null, n|null)` (store.js) writes the
  machine or exercise goal on the layout read IN THE TAP (the
  `setAssistGoal` pattern); `null` deletes; `exerciseSets` is pruned when
  empty.
- Cardio sets may carry `level` (whole number ≥ 1; absent = none; never 0 or
  `null`). `SET_NUMBERS` gains `'level'` so untrusted input repairs it; unit
  conversion never touches it. The plan-target shape `{distance, seconds}`
  may carry `level` too.
- A slot grown by opening a machine (log screen push, overview picker,
  `firstMachineId`) carries `free: true`. A free slot with no set logged is
  where you merely stood, not a commitment: `nextOpenSlot` skips it, the
  overview still lists it. Slots from `startWorkoutFrom`'s source (plan or
  repeat) carry no marker.
- A slot's SET GOAL is computed, never stored: `slotGoal(active, slot,
  layout, s)` = `slot.target?.sets ?? setGoalFor(machine, slot.exercise, s)`
  (null when the slot is unbound, its machine gone, or cardio). `slotDone`
  = goal ? count ≥ goal : count > 0. The slot shape stays as it is (the
  tests pin it by `deepEqual`; a stored goal would also go stale when the
  setting changes mid-workout). A goal changed ON the log screen for this
  workout is written as `slot.target.sets` — a sets-only target `{sets}` is
  a legal target shape from now on (no reps → no prefill from it).
- Icons are presentation: `machineIcon(machine)` lives in **ui.js** (it
  imports `MUSCLE_REGIONS` from store.js; ui.js already imports store.js).
  map.js imports it from ui.js next to `esc` — update the architecture
  note that says map.js imports "only esc".

## Feature designs

### F1 — Icons (agent A)

- `machineIcon(machine)` in ui.js, data-driven:
  - `machine.cardio`: by label, first match wins — treadmill/run → 🏃,
    bike/cycle/spin/ergometer → 🚴, row → 🚣, stair/step/climb → 🪜,
    ski → ⛷️, swim → 🏊, elliptical/cross → 🏃; no match → ❤️.
  - else the region of the FIRST primary muscle (`MUSCLE_REGIONS` order is
    irrelevant — the machine's own `muscles[0]`): Chest 🫁, Back 🧗,
    Shoulders 🤷, Arms 💪, Core 🧘, Legs 🦵, Full body 🏋️.
  - no primary muscle: bodyweight → 🤸, else 🏋️.
  Exported; `REGION_ICONS` and `CARDIO_ICONS` exported for the tests.
- Shown as `<span class="machine-icon" aria-hidden="true">…</span>` right
  after the number badge — decorative, the number and label stay the
  information: the overview's `.plan-row`, the log screen's
  `.machine-head`, the plan builder's `.plan-item-head`, History's workout
  list entry lines and the editor's entry titles, the Gym's machine card
  title and the list editor's rows, the quick-switch chips and the Next
  button on the log screen.
- The floor map (map.js `drawLayout`): the icon as a small `<text>` in the
  machine box's top-left corner (font-size ≈ 0.55 × the number's, only when
  the box is at least 3 units on both sides, `pointer-events="none"`), in
  every mode (colors, usage, path, editor). Escaped like everything else.
- CSS: `.machine-icon` ~18px, fixed width, `flex-shrink: 0`; nothing
  focusable, so no 44px rule applies.
- Tests: ui.test.mjs (the icon matrix incl. the fallbacks), map.test.mjs
  (the icon text is in the svg, and not for a 2×2 box), one assertion each
  in train/plan/history/gym tests that a row carries `.machine-icon`.

### F2 — "Next" in a free workout (agent B, with F3)

- `nextOpenSlot` keeps its contract for committed slots and additionally
  skips a `free` slot with no set.
- New `suggestNext(active, layout, machine, { workouts, earlier })` in
  train.js (exported for the tests), used when `nextOpenSlot` finds nothing
  and the workout is not pinned to a plan slot:
  1. Candidates: machines of the layout not trained today — no set in this
     workout, none in a workout finished today (`finishedToday()`), not the
     current machine.
  2. History successor: stats.js `transitionCounts(workouts, layout)` from
     this machine; the candidate with the highest count wins; ties by the
     shorter walk (`walksCached`, straight line when there is no walkable
     grid), then by `num`.
  3. Else the candidate with the most OPEN primary muscles
     (`trainedMuscles(active, layout, earlier)`), same tie-breaks; a machine
     without tags counts as one open muscle (the 🎲 rule).
  4. Nothing → null (the log screen shows "Workout overview →" as today).
- Rendering: the plan's slot renders "Next: …" as before; a suggestion
  renders the same `#next-machine` button reading "Try next: #N Label →"
  with `data-suggested="1"`, no "Busy?" row and no "Closer:" hint (both
  describe a plan's next stop). The tap pushes a `{machineId, exercise:
  null, free: true}` slot when none exists and `switchMachine`s. The rest
  overlay's promise (`nextUpLabel`) says the same.
- Tests (train.test.mjs): a free workout A(3 sets)·B(opened, 0 sets)·C on
  screen → Next is not B; with history where D usually follows C, Next
  names D; without history the machine with the most open muscles; every
  machine trained → no Next button, overview button instead.

### F3 — Set goals (agent B)

- Settings → Workout card: "Sets per exercise" stepper `#default-sets`
  (step 1, min 1) next to the rest timer; `change` writes
  `settings.defaultSets` (whole number ≥ 1).
- Gym machine card: a "Sets per visit" number field `#m-sets`
  (placeholder `(3)` = the default; empty deletes `targetSets`; hidden for
  cardio) and, when `exerciseSets` exists, one muted line "Per exercise:
  Curl 4 · Row 2". Removing an exercise chip prunes its entry. The list
  editor gets nothing.
- train.js: `slotGoal`/`slotDone` as in the data model; every caller of
  `slotDone`/`slotSetCount` (17 sites) passes `layout` and the render's
  settings. `twinShare` deals by the goal, not `target.sets || 1`.
  `targetTally` counts every slot with a goal, so a free workout's overview
  line reads "6/9 target sets" too. The log screen: `setGoal` is the slot's
  goal (the "set 1/3" in the log button and the Next takeover now work in
  free workouts — that IS the ask); the "Target:" head line reads
  "Goal: 3 sets · set 1/3" when the slot has no plan target but a goal.
  The overview rows read "1/3 sets" / "✓ 3/3 sets", and the Exercises card
  header counts "2 of 5 done".
- Log screen control: a "Sets planned" stepper `#set-goal` (numeric, min 1)
  after Rest, not for cardio. `change` sets `currentSlot.target = { ...,
  sets: v }` on the WORKOUT (no re-render — the + is under the thumb; the
  log label and head line refresh in place like `refreshLogLabel`), and a
  "Keep 4 sets for #7[ · Curl]" link (`#sets-keep`, hidden while the value
  equals `setGoalFor` of the machine) writes it through `setTargetSets` —
  for the slot's exercise when it has one, else the machine; a value equal
  to the app default deletes instead of pinning (the rest's rule).
- Tests: store (precedence, lifecycle, refusal, cleanSettings,
  USER_SETTINGS), train (done after 3, log label "1/3", Next primary after
  the goal, the stepper and Keep), settings (stepper saves), gym (field
  and pruning).

### F4 — Session progress bars (agent C)

- The overview's "Muscles today" card becomes bar rows: one `.muscle-row`
  per muscle of `layoutMuscles(layout)` in `MUSCLE_REGIONS` order (unknown
  muscles last), value = sets this workout counting a primary set as 1 and
  a secondary as ½ (`usageByMuscle([active], layout)` gives both), bar
  length relative to the busiest muscle (History's rule), label
  "Chest · 3 sets" / "Hamstrings · 1½" / "open" at 0. A line above the
  rows: "4 of 9 muscles trained". The rows stay tappable
  (`data-muscle`, `#muscle-coverage` keeps its id) and drive the picker's
  muscle filter as the chips did. Reuse `.muscle-row`/`.bar-track`/
  `.bar-fill`; a 0 row gets `.open` (muted label, empty track).
- The log screen's "Workout overview →" button gains the same count as a
  `.sub`: "4/9 muscles" — one glance without leaving the machine.
- Tests: train.test.mjs replaces the chip pins with row pins (count,
  order, the ½, the tap filtering the picker).

### F5 — Cardio levels (agent D)

- Log screen (cardio only): third stepper "Level" `#set-level` (numeric,
  step 1, min 0; 0 = none). `readCardio()` adds `level` only when > 0;
  `nextSetDefaults` carries the previous set's / target's level; `setWords`
  and ui.js `setStr` append " · L5"; the log label says it.
- History editor: a third cardio field `.edit-level` (number, aria-label
  "Level"); empty or 0 deletes it on save; "+ Set" copies it with the rest.
- Plan text: `L5` / `level 5` / `lvl 5` after a cardio line ("Rower 20min
  L5") → `target.level`; `planToText` writes it back; the builder's target
  fields get nothing (the Text view sets it).
- AI export: a cardio tuple's FOURTH element is the level when present
  (`[distance, seconds, sec|null, level]`); the prompt and the export note
  say so. The paste-back grammar reads `level` on cardio targets.
- Tests: store/untrusted (repair, markup dropped), ui (setStr), train
  (stored, absent at 0, prefilled), history (editor round-trip), plan
  (parse/serialise), ai (the tuple).
